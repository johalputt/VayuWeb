## Abstract

`CHANGELOG.md` states that the project's version scheme "will be set by a VWIP before the first
tag, not improvised at tag time". This is that proposal.

It defines two version numbers that are deliberately not the same thing — a **protocol version**
carried in every record, and an **implementation version** on the software that speaks it — and
it fixes when each may change. It also sets the release discipline: what must be true before a
tag exists, and what a version number is permitted to imply.

## Motivation

A version number is a promise made to people who are not in the room. Two failure modes follow
from getting it wrong, and they pull in opposite directions.

**Conflating protocol and implementation.** If one number covers both, then a bug fix in the
reference implementation looks like a protocol change to anyone tracking compatibility, and a
genuine wire change can hide inside a routine release. `version` in a record is `1`, and it
must stay `1` until the wire format actually changes — regardless of how many times the software
that writes it is released.

**Publishing a number that implies more assurance than exists.** VayuWeb's charter promises
properties — no privileged writer, no seizure path, verification without trust — that no test
suite can fully establish. A tag says "this is a thing you may depend on". Cutting one before
the project can support that reading is not a versioning mistake; it is a false statement about
software people may run in front of hostile parties.

There is a third motive, specific to this project. Article 44.6 requires that a second
implementation can be built from the specifications alone. Until one exists, no version of this
implementation can be called a reference, because "reference" means other things were checked
against it and nothing has been.

## Specification

### 1. Two version numbers

1.1 The **protocol version** is the `version` field of a registry record, defined in
[REGISTRY.md](REGISTRY.md). It is an unsigned integer, currently `1`.

1.2 The protocol version MUST change only through a Standards Track VWIP that alters something
observable between independent implementations. It MUST NOT change because the implementation
changed.

1.3 A verifier MUST reject a protocol version it does not implement, per REGISTRY.md. It MUST
NOT attempt to interpret an unknown version on a best-effort basis.

1.4 The **implementation version** identifies a release of software in this repository. It
follows Semantic Versioning 2.0.0 and is independent of the protocol version.

### 2. Implementation versioning

2.1 Releases are tagged `vMAJOR.MINOR.PATCH`, matching `registry/package.json`.

2.2 Before `1.0.0`, the public interface is explicitly unstable: a MINOR release MAY break it.
This is the honest reading of a pre-implementation project, and it MUST NOT be represented
otherwise in documentation or release notes.

2.3 From `1.0.0`:

- **MAJOR** — a breaking change to a published interface: the command-line surface, the exported
  module API, the log file format, or the conformance vector schema.
- **MINOR** — new capability, backwards compatible.
- **PATCH** — a fix that changes no interface.

2.4 A change to a **verification rule** is a MAJOR change even when the code compiles against
the same API, because it changes which records a peer accepts, and a peer that accepts a
different set is a different implementation of the protocol whatever its API looks like.

2.5 Release notes MUST state the protocol version the release speaks. A release that changes
the accepted record set without changing the protocol version MUST say so explicitly, since
that combination is the one most likely to surprise.

### 3. Pre-conditions for a tag

3.1 A tag MUST NOT be created unless all of the following hold:

1. Every CI workflow passes on the commit being tagged.
2. The conformance vectors in `conformance/vectors.json` pass, and the committed artifact
   matches a fresh generation.
3. An adversarial review has been run over everything accumulated since the previous tag, and
   its outcome — including "nothing found" — is recorded in `CHANGELOG.md`.
4. `CHANGELOG.md` has a section for the version, and it names every defect found in the
   **specifications** as well as in the code.

3.2 Condition 3 is not satisfied by a code review. A review asks whether the code does what it
says; an adversarial pass asks what an attacker would do to it. Implementing this specification
has so far produced six defects of the second kind and none of the first, which is the argument
for keeping them separate.

3.3 A defect found during 3.1(3) MUST be fixed before the tag, not after it. A release known to
contain a hole, shipped because the fix "can go in the next one", is a decision nobody would
defend out loud.

### 4. What a version number may claim

4.1 No release before `1.0.0` may be described as production-ready, audited, or a reference
implementation.

4.2 The term **reference implementation** MUST NOT be applied to any version until a second,
independent implementation exists and the two agree on the full conformance vector set. Until
then this is *an* implementation, and the specifications — not the code — are authoritative when
they disagree.

4.3 A release MUST NOT claim conformance to a specification area that has no test vectors.
Replication, convergence and resolution currently have none. Absence of vectors is not evidence
that an area is settled, and a release note MUST NOT read as though it were.

### 5. Protocol version 1 and its successors

5.1 Protocol version `1` is the format described by REGISTRY.md at the time of the first tag.

5.2 A Standards Track VWIP proposing protocol version `2` MUST specify what a version-1 verifier
does on encountering a version-2 record (reject, per 1.3), what a version-2 verifier does with
version-1 records, and whether both may coexist in one log.

5.3 Such a VWIP MUST include an activation epoch strictly in the future, per Article 47 and
VWIP-0000 section 3.

## Security considerations

The rule that matters here is 3.3. A versioning process that permits shipping a known hole
converts the release into a statement the project knows to be false, and the people harmed are
the ones who trusted the number rather than reading the diff.

Rule 2.4 exists for a subtler reason. A change to a verification rule that keeps the API stable
looks like a patch and is a fork: two peers on different versions accept different record sets
and diverge without either logging an error. Treating it as MAJOR makes the divergence visible
before it is deployed rather than after.

Rule 4.2 is a security control despite reading like a documentation rule. "Reference
implementation" invites others to defer to this code where it disagrees with the specification.
Deferring to code that has never been checked against a second implementation is precisely the
monoculture the charter's independence requirement exists to prevent.

## Privacy considerations

Release artifacts and tags are public and permanent. Release notes MUST NOT include contributor
email addresses beyond what the commit history already carries, deployment hostnames, or the
identities of anyone who reported a defect without asking to be named. A version number should
carry no information about who runs the software or where.

The `Author` field of a VWIP may be a persistent pseudonym with exactly the standing of a
named author, per VWIP-0000 section 1.2; nothing in this proposal narrows that.

## Impossibility-and-capture analysis

**What this makes impossible.** It makes it impossible to cut a release that silently changes
which records are accepted: rule 2.4 forces such a change to be MAJOR, and rule 2.5 forces the
release notes to say so.

**What this makes worth capturing.** The tag itself. Whoever can create a tag can make a
statement about assurance that users will act on. This proposal deliberately does not create a
release authority, because that would be the thing worth capturing; it instead makes the
pre-conditions mechanically checkable — CI status, vector agreement, a changelog section — so
that a tag created without them is detectable by anyone, after the fact, from the repository
alone.

The residual risk is honest: a determined tagger can write "adversarial review: nothing found"
without having run one. No process fixes that. What the requirement buys is that the claim is
recorded, attributable and falsifiable rather than merely absent.

## Centralisation analysis

Parties whose withdrawal would degrade this mechanism:

- **The repository host.** Tags and CI live on GitHub today. Withdrawal would remove the
  automated pre-conditions in 3.1(1). Justified as temporary: `docs/ROADMAP.md` Phase 6 moves
  development to Radicle, and the conditions in 3.1 are stated so that they can be checked by
  hand from a clone if no CI exists.
- **Nobody else.** The version scheme itself requires no registry, no service and no authority.
  A fork can apply this proposal to its own tags without asking anyone.

## Migration and rollback

There is nothing to migrate: no tag exists yet. This proposal takes effect on the first one.

Rollback is a superseding Process VWIP. Because no protocol behaviour depends on this document,
withdrawing it cannot invalidate any record, break any log, or partition any peer — the reason
it is Process rather than Standards Track.

## Activation epoch

On acceptance, and in any case before the first `v*` tag is created. No protocol activation
epoch is required, because nothing observable between implementations changes. Should a future
protocol version be proposed under section 5, that VWIP carries its own epoch strictly in the
future per Article 47.

## Expiry of transitional mechanisms

One transitional mechanism is created here: **rule 2.2**, the pre-`1.0.0` regime in which MINOR
releases may break the public interface.

It expires on the `1.0.0` tag, and MUST NOT be extended past it by convention or silence. If
`1.0.0` proves premature, the answer is a superseding VWIP that says so in the open, not a
`0.x` series continued indefinitely so the promise never comes due.

## Test vectors

None, and this is the case where "none" is the correct answer rather than an omission: a Process
proposal changes nothing observable between independent implementations, so there is nothing for
a vector to pin. VWIP-0000 section 3 requires vectors "for anything observable on the wire", and
this proposal is deliberately outside that set — which is exactly why it is Process and not
Standards Track.

The pre-conditions in section 3.1 are nevertheless mechanically checkable, and 3.1(1) and
3.1(2) are already enforced by CI on every commit.
